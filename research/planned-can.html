Spotting intruders on the car's internal network

Inside every car, dozens of computers talk over one shared bus with no sender authentication. This project builds detectors that notice when a message on that bus does not belong there.

The question

Can a detector notice when a message on a car's internal bus does not belong there?

Why it matters

Dozens of control units share one bus with no sender authentication, and an attacker who reaches it can control brakes, engine and locks.

How we will test it

Benchmark timing, content and learning detectors on public in-vehicle datasets, test them on another car or software version, and profile them on gateway-class hardware.

Why this matters

Researchers have shown that an attacker who reaches a car's internal network can control brakes, engine and locks. Messages on that network carry no proof of who sent them, so detection has to come from patterns: when messages arrive, what they contain and which control unit produced them. My PredriveID work with General Motors Research read exactly this kind of bus data to tell drivers apart, using low-cost hardware. This project turns the same skills toward catching intrusions.

Research questions

  1. How well do timing-based, content-based and learning-based detectors catch injection, flooding and impersonation attacks on public in-vehicle datasets?

    Hypothesis
    Timing detectors catch flooding and most injections cheaply; impersonation that keeps the rhythm needs content or sender features.
    How we would test it
    Benchmark the three families on public in-vehicle datasets with one common split and per-attack metrics.

  2. Do detectors trained on one car still work on another model, or after a software update changes the message rhythm?

    Hypothesis
    Learned detectors transfer poorly across vehicles; timing baselines recover after recalibrating on a short drive.
    How we would test it
    Train on one vehicle or software version, test on another, and measure how much clean driving each detector needs to recover.

  3. Can a detector small enough for an in-vehicle gateway also say which control unit sent the bad message?

    Hypothesis
    Timing and electrical traits together can point to the sending control unit for many attacks.
    How we would test it
    Add sender attribution and test it on data with known sources, then profile it on gateway-class hardware.

Expected contributions

  • A common benchmark of in-vehicle intrusion detectors across attack types.
  • Measurements of how detectors transfer across vehicles and software updates.
  • A gateway-sized detector that also points to the sending control unit.

Approach

  1. DatasetsStart from public in-vehicle attack datasets, then log our own drives with an OBD-II interface.
  2. BaselinesReimplement entropy, clock-skew and neural detectors from the reading list.
  3. Cross-car testsTrain on one vehicle or time period, test on another.
  4. Lightweight modelShrink the best detector for a low-cost embedded board.
  5. ReportDetection rate, false alarms per hour of driving and attribution accuracy.

Discussion

If it works

A detector small enough for a car's gateway catches injected messages quickly.

Where it could fail

  • Public bus datasets cover few cars and simple attacks, and a careful attacker can copy normal timing.
  • A false alarm in a car is costly, so thresholds have to be conservative.

How we will know

Detection and false-alarm rates across attack types, and latency on embedded hardware.

Start here

A first month for a student joining this work, in 4 steps. Do them in order: each one uses what the one before produced.

Goal for the month: A timing-based intrusion detector for the car's internal network, tested offline and on a live virtual bus.

Before you start: setup for every project
  1. Set up a workspace. Create a private Git repository for the project with folders for data/, src/, figures/ and notes/. Make a Python virtual environment (python -m venv .venv) and record every package you install in requirements.txt.
  2. Keep a lab notebook. Add a dated entry to notes/log.md each time you work: what you ran (the exact command), what came out, and what surprised you. This log is the first thing to share when you ask for help, and most of your paper's method section comes from it.
  3. Make every number reproducible. Fix random seeds, write down the dataset version and how you split it, and keep the script that produced each figure next to the figure. If you cannot regenerate a number with one command, it is not finished.
  4. Stay legal and ethical. Work only with public datasets, data you recorded yourself with everyone's consent, or systems you own. Never test an attack on a network, car, radio band or service that is not yours, and follow the safety note on this page.
  5. When you get stuck. Spend about an hour, then write down what you tried, what you expected and the exact error or plot, and ask. A precise question is much easier to answer than "it does not work".
  1. Step 1 · Week 1Read the papers
    • Read the papers below.
    • Write down which attacks each detector catches and which it misses.

    You are done when you have a table of attacks vs detectors.

  2. Step 2 · Week 2Look at message timing
    • Download the HCRL Car-Hacking dataset.
    • For each CAN identifier in the normal data, plot the time between consecutive frames.

    You are done when you can see that most identifiers repeat at a steady period.

  3. Step 3 · Week 3Write the detector
    • Flag a frame when its identifier arrives much sooner than its normal period.
    • Report detection rate and false alarms for each attack type in the dataset (DoS, fuzzy, spoofing).

    You are done when one table gives results per attack type.

  4. Step 4 · Week 4Test it live
    • Set up a virtual CAN interface on Linux and replay a log onto it with can-utils.
    • Run your detector on the live stream and confirm it raises the same alarms as offline.

    You are done when live and offline alarms match on the same log.

Tools and data

  • HCRL Car-Hacking datasetCAN traffic from a real car with injection attacks.
  • can-utilsLinux SocketCAN tools for logging and replaying CAN traffic.

Finished the month? Email me your log, your figures and one paragraph on what you would do next. Writing it up? Follow the LaTeX and Overleaf guide for templates, citations, figures and the checks to run before you submit.

Skills you will use and learn

  • Time-series anomaly detection
  • Embedded boards (Raspberry Pi or similar)
  • Careful experiment design

Papers to read first

  1. Experimental security analysis of a modern automobile
    K. Koscher, A. Czeskis, F. Roesner, S. Patel, T. Kohno, S. Checkoway, D. McCoy, B. Kantor, D. Anderson, H. Shacham, S. Savage
    IEEE S&P, 2010
    The paper that showed what an attacker on the car's network can do.
    Read
  2. Entropy-based anomaly detection for in-vehicle networks
    M. Müter, N. Asaj
    IEEE Intelligent Vehicles Symposium, 2011
    An early, simple detector that is still a useful baseline.
    Read
  3. Fingerprinting electronic control units for vehicle intrusion detection
    K.-T. Cho, K. G. Shin
    USENIX Security, 2016
    Uses the timing of periodic messages to fingerprint the sender.
    Read
  4. GIDS: GAN based intrusion detection system for in-vehicle network
    E. Seo, H. M. Song, H. K. Kim
    PST, 2018
    A learning-based detector that can flag attacks it never saw.
    Read
  5. In-vehicle network intrusion detection using deep convolutional neural network
    H. M. Song, J. Woo, H. K. Kim
    Vehicular Communications, 2020
    A deep detector evaluated on a widely used public dataset.
    Read
  6. PredriveID: Pre-trip driver identification from in-vehicle data
    G. Kar, S. Jain, M. Gruteser, J. Chen, F. Bai, R. Govindan
    ACM/IEEE SEC, 2017
    How we collected and used in-vehicle bus data.
    Read
