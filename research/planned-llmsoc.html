Can a language model help triage security alerts?

Security teams face far more alerts than they can read, and most turn out to be harmless. This project tests whether a language model that reads the context around each alert can put the real incidents first, and how to catch it when it gets the facts wrong.

The question

Can a language model that reads the records around each alert put real incidents ahead of false alarms?

Why it matters

Analysts are buried in false positives, and a confident wrong answer can close a real incident.

How we will test it

Replay labeled alerts, rank them by rule severity, by a model alone and by a model with retrieved context, and check every claim the model makes against the records.

Why this matters

Analysts in security operations centers report being buried in false positives, and rule-based severity labels are a weak guide to what matters. Language models can read an alert together with asset records, recent tickets and related events, which is what an experienced analyst does. They can also state context that is not there, and an attacker who controls a log field can try to talk to them.

Our university chatbot answers questions from retrieved university pages, and the planned chatbot-security project studies how retrieval can be poisoned. This project moves the same ideas into security operations, where a confident wrong answer can close a real incident.

Research questions

  1. Does retrieving context for each alert make a language model rank alerts better than rule severity, within a fixed analyst budget?

    Hypothesis
    Adding asset records, recent tickets and related alerts lets the model separate real incidents from noisy rule hits better than severity labels alone.
    How we would test it
    Replay labeled alerts from public datasets and lab attacks, rank them with rules, a model without context and a model with retrieved context, and compare how many real incidents fall within a fixed analyst budget.

  2. How often does the model invent or misread context, and can a check against the source records catch it?

    Hypothesis
    Most errors come from context the model claims but the records do not contain; checking each claim against the retrieved records catches many of them.
    How we would test it
    Label every factual claim in the model's triage notes against the source records, then measure how many unsupported claims a second-pass checker flags.

  3. Can an attacker steer the triage model through the alert data itself, and how well does isolating untrusted fields defend against it?

    Hypothesis
    Text an attacker controls, such as a file name or a log message, can carry instructions into the model; isolating untrusted fields reduces this.
    How we would test it
    Plant instruction-like strings in log fields and measure how often alerts are wrongly closed, with and without input isolation.

Expected contributions

  • An alert-triage test set with labeled incidents and analyst-style context records.
  • A measured comparison of rule, model and retrieval-based triage at fixed analyst budgets.
  • A claim checker for triage notes, and tests of prompt injection through alert fields.

Approach

  1. AlertsBuild a labeled alert set from public datasets and attacks staged in our lab.
  2. ContextAdd the records an analyst would check: assets, tickets, related alerts.
  3. RankCompare rules, a model alone and a model with retrieved context.
  4. CheckVerify every claim in the model's notes against the records.
  5. AttackPlant instruction-like text in log fields and measure the effect.

The project uses lab and public data only; no real organization's alerts or logs.

Discussion

If it works

Analysts read the real incidents first, and the model's mistakes are caught before they matter.

Where it could fail

  • Language models can state wrong facts with confidence.
  • Alert data is sensitive, so models may need to run locally.

How we will know

How high real incidents rank, how often the model's stated facts are wrong, and analyst time saved in a simulated queue.

Start here

A first month for a student joining this work, in 4 steps. Do them in order: each one uses what the one before produced.

Goal for the month: A first test of whether a language model with context ranks security alerts better than severity alone.

Before you start: setup for every project
  1. Set up a workspace. Create a private Git repository for the project with folders for data/, src/, figures/ and notes/. Make a Python virtual environment (python -m venv .venv) and record every package you install in requirements.txt.
  2. Keep a lab notebook. Add a dated entry to notes/log.md each time you work: what you ran (the exact command), what came out, and what surprised you. This log is the first thing to share when you ask for help, and most of your paper's method section comes from it.
  3. Make every number reproducible. Fix random seeds, write down the dataset version and how you split it, and keep the script that produced each figure next to the figure. If you cannot regenerate a number with one command, it is not finished.
  4. Stay legal and ethical. Work only with public datasets, data you recorded yourself with everyone's consent, or systems you own. Never test an attack on a network, car, radio band or service that is not yours, and follow the safety note on this page.
  5. When you get stuck. Spend about an hour, then write down what you tried, what you expected and the exact error or plot, and ask. A precise question is much easier to answer than "it does not work".
  1. Step 1 · Week 1Read the studies
    • Read the SOC analyst study and the papers below.
    • Write down how analysts decide which alert to look at first.

    You are done when you have a short list of what analysts weigh.

  2. Step 2 · Week 2Pick the alerts
    • Set up the Boss of the SOC v3 data following its repository instructions.
    • Pick twenty alerts whose outcome is known (real incident or not).

    You are done when you have twenty alerts with labels in one file.

  3. Step 3 · Week 3Rank two ways
    • Rank the alerts by severity.
    • Rank them again with a language model that also sees retrieved context (related logs and asset notes).
    • Count the real incidents in the top five of each ranking.

    You are done when one table compares the two rankings.

  4. Step 4 · Week 4Label consistently
    • Map each real incident to MITRE ATT&CK techniques.
    • Check that the model's explanations name techniques that match your labels.

    You are done when every incident has ATT&CK labels and a note on whether the model agreed.
