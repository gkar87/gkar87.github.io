Tamper-evident identity for IoT devices on a blockchain

A network should know which devices are allowed on it and notice when one is cloned or tampered with. This project records device identities on a permissioned blockchain and checks live traffic against them.

The question

Can a ledger of device identities, checked against live traffic, catch cloned or tampered IoT devices?

Why it matters

A cloned device can present a valid credential; the network should notice that it behaves like something else and revoke it everywhere.

How we will test it

Stage cloning, spoofing and tampering attacks in an IoT testbed, compare detection by the ledger check, the traffic check and both, and load-test the ledger on fog-class hardware.

Why this matters

Our systematic review of hybrid blockchain platforms for IoT (Sensors, 2022) found a fast-growing field in which most systems pair the ledger with cloud or fog computing, but few test how identity checks hold up against real attacks. Separately, my group identifies an IoT device's vendor and type from a single packet header. Putting the two together gives a concrete idea: a ledger that every gateway can read records each device's credential, firmware hash and expected traffic fingerprint, so a device that claims the right name but behaves like something else can be caught and revoked network-wide.

Research questions

  1. Does combining a ledger credential with a traffic fingerprint catch cloned, spoofed or tampered devices better than either check alone?

    Hypothesis
    The two checks fail in different ways, so together they catch clones that pass either one alone.
    How we would test it
    Stage cloning, spoofing and tampering attacks in an IoT testbed and compare detection by each check and by both.

  2. How many devices and identity checks per second can a permissioned ledger on fog nodes handle before it becomes the bottleneck?

    Hypothesis
    Edge identity checks fit within a permissioned ledger's capacity if fingerprint baselines are updated in batches.
    How we would test it
    Load-test the ledger on fog-class hardware with growing device counts and update rates.

  3. Which attacks on the smart contracts and on the gateways themselves undermine the scheme, and which design rules prevent them?

    Hypothesis
    A compromised gateway, not the ledger, is the weak point.
    How we would test it
    Threat-model the system, run known contract and gateway attacks, and turn what succeeds into design rules.

Expected contributions

  • A prototype that pairs ledger credentials with traffic fingerprints.
  • Capacity measurements on fog-class hardware.
  • Design rules from attacks on the contracts and gateways.

Approach

  1. DesignChoose what goes on the ledger: credential, firmware hash, fingerprint summary.
  2. BuildSmart contracts on Hyperledger Fabric, with Raspberry Pi gateways and real IoT devices.
  3. AttackClone, spoof and reflash devices; attack the contracts.
  4. MeasureDetection rate, false alarms, latency and throughput as devices scale.
  5. ReportOpen code and a threat model others can reuse.

Discussion

If it works

The network notices a cloned or tampered device by checking its behavior against a record nobody can quietly change.

Where it could fail

  • Ledger overhead may be too high for small networks.
  • Fingerprints drift, so updates must be authorized without opening a door for attackers.

How we will know

How often clones are caught, ledger latency, and the cost per device.

Start here

A first month for a student joining this work, in 3 steps. Do them in order: each one uses what the one before produced.

Goal for the month: A device registry on a permissioned blockchain, and a test of whether a traffic fingerprint catches a cloned device.

Before you start: setup for every project
  1. Set up a workspace. Create a private Git repository for the project with folders for data/, src/, figures/ and notes/. Make a Python virtual environment (python -m venv .venv) and record every package you install in requirements.txt.
  2. Keep a lab notebook. Add a dated entry to notes/log.md each time you work: what you ran (the exact command), what came out, and what surprised you. This log is the first thing to share when you ask for help, and most of your paper's method section comes from it.
  3. Make every number reproducible. Fix random seeds, write down the dataset version and how you split it, and keep the script that produced each figure next to the figure. If you cannot regenerate a number with one command, it is not finished.
  4. Stay legal and ethical. Work only with public datasets, data you recorded yourself with everyone's consent, or systems you own. Never test an attack on a network, car, radio band or service that is not yours, and follow the safety note on this page.
  5. When you get stuck. Spend about an hour, then write down what you tried, what you expected and the exact error or plot, and ask. A precise question is much easier to answer than "it does not work".
  1. Step 1 · Week 1Read the review
    • Read our hybrid blockchain review and the papers below.
    • Write down what a blockchain adds for device identity and what it does not solve.

    You are done when you can explain why a valid credential alone does not prove the device is genuine.

  2. Step 2 · Weeks 2 and 3Set up the network
    • Install Hyperledger Fabric and bring up its test network following the official tutorial.
    • Write a smart contract (chaincode) that stores and reads a device record.

    You are done when you can add a device record and read it back from the command line.

  3. Step 3 · Week 4Add a fingerprint and test a clone
    • Extract a small traffic fingerprint with Scapy and store it in the device record.
    • Simulate a cloned device that has the right credential but different traffic, and check whether your contract flags it.

    You are done when one test shows the real device accepted and the clone flagged.
