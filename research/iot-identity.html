IoT device identity and network incidents

A network that cannot tell which device sent a packet, or whether that device was tampered with, cannot defend itself. We identify devices and attacks from packet headers alone.

The question

Can a network tell which device sent a packet, and which attack it is facing, from packet headers alone?

Why it matters

Vulnerable IoT devices have to be found and isolated quickly, without installing software on them.

What we found

One packet's header named the device with 95.3% weighted accuracy, and features chosen by a genetic algorithm caught two denial-of-service floods every time and DNS botnets and OS scans about 95% of the time.

Fingerprinting IoT devices from a single packet

With Dr. Ahmet Aksoy and UCM students, we identify an IoT device's vendor and type from the header fields of just one TCP/IP packet, so vulnerable devices can be found and isolated quickly. We compared feature selection methods from four families (filter, wrapper, embedded and search optimization) to learn which header fields carry the fingerprint.

Identifying network attacks with a genetic algorithm

Instead of experts hand-picking traffic features, a genetic algorithm evolves the feature subset: each candidate is scored on how accurately a classifier separates attack from normal traffic and on how few features it needs. The result detects DNS botnets, two kinds of denial-of-service floods and NMAP OS scanning. The code and data are public.

Hybrid blockchains for IoT

With my M.Sc. student Ahmed Alkhateeb, we systematically reviewed how hybrid blockchain platforms secure IoT data. Ethereum dominates, and most systems pair the ledger with cloud or fog computing.

Where this is going

Combining traffic fingerprints with ledger-based attestation, so a network knows which devices are present and whether any has been tampered with, cheaply enough for resource-constrained IoT deployments.

Discussion

What it shows

One packet's header fields carried enough of a device's habits to name it most of the time (95.3% in our study), and a genetic algorithm found the small set of features that tell network attacks apart.

Where it falls short

  • Header fingerprints can pick up details of the capture, such as addresses and timestamps, instead of the device itself.
  • Devices change with firmware updates, so a fingerprint learned once drifts.
  • More traffic is encrypted every year, which limits what headers alone can say.

What it means

Network operators can build a device inventory from traffic they already collect, with no software on the devices. The leak-free benchmark and encrypted-traffic projects test how far that holds.

Open research questions

Questions this work leaves open. They are directions, not results; each links to the planned project that takes it up.

  1. How can traffic-fingerprint baselines be kept current cheaply enough for resource-constrained IoT deployments?

    Why it is open
    Device behavior drifts with firmware updates and usage, and constrained networks cannot afford constant retraining.
    Taken up in
    ledger identity · leak-free benchmarks

  2. Can devices and applications be identified from encrypted-flow metadata alone, without decrypting payloads?

    Why it is open
    Most traffic is now encrypted, so sizes, timing and handshakes are what a privacy-respecting network can still use.
    Taken up in
    encrypted traffic

  3. Can a device's radio signature back up its traffic fingerprint, so that a clone has to fake both?

    Why it is open
    Header fingerprints identify a device's type from its packets. A cloned device can copy packets more easily than it can copy the flaws of another radio.
    Taken up in
    RF fingerprinting

Start here

A first month for a student joining this work, in 3 steps. Do them in order: each one uses what the one before produced.

Goal for the month: A device classifier that names IoT devices from packet headers, and a list of the header fields it depends on.

Before you start: setup for every project
  1. Set up a workspace. Create a private Git repository for the project with folders for data/, src/, figures/ and notes/. Make a Python virtual environment (python -m venv .venv) and record every package you install in requirements.txt.
  2. Keep a lab notebook. Add a dated entry to notes/log.md each time you work: what you ran (the exact command), what came out, and what surprised you. This log is the first thing to share when you ask for help, and most of your paper's method section comes from it.
  3. Make every number reproducible. Fix random seeds, write down the dataset version and how you split it, and keep the script that produced each figure next to the figure. If you cannot regenerate a number with one command, it is not finished.
  4. Stay legal and ethical. Work only with public datasets, data you recorded yourself with everyone's consent, or systems you own. Never test an attack on a network, car, radio band or service that is not yours, and follow the safety note on this page.
  5. When you get stuck. Spend about an hour, then write down what you tried, what you expected and the exact error or plot, and ask. A precise question is much easier to answer than "it does not work".
  1. Step 1 · Week 1Read our two papers
    • Read our ICISSP 2024 and Electronics 2024 papers below.
    • List which header fields each one uses and why those fields differ between devices.

    You are done when your list maps each field to a reason it identifies a device.

  2. Step 2 · Week 2Capture your own traffic
    • Capture a few minutes of traffic from two devices you own (a phone and a smart plug, for example) with Wireshark.
    • Load the capture with Scapy and pull out the header fields from your list into a table, one row per packet.

    You are done when you have a CSV of header fields from your own two devices.

  3. Step 3 · Weeks 3 and 4Classify and inspect
    • Train a nearest-profile classifier on the header fields of CICIoT2023 devices.
    • Measure accuracy per device, then remove one field at a time and record the drop.

    You are done when one chart shows which fields the classifier leans on most.
