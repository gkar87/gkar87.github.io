Attacking and defending a campus chatbot

Chatbots that answer from a university's own pages are spreading fast. This project red-teams one: can a planted page or a crafted question make it give wrong or harmful answers, and which defenses hold up?

The question

Can a planted web page or a crafted question make a campus chatbot give wrong or harmful answers?

Why it matters

Universities are putting these chatbots in front of students for admissions, aid and IT help, and they trust whatever they retrieve.

How we will test it

Red-team a sandboxed copy of our chatbot, compare keyword-plus-vector retrieval with vector search alone, and measure what each defense blocks and what it costs.

Why this matters

My students and I recently built a retrieval-augmented chatbot for UCM from the university's own web pages (manuscript submitted). Systems like it read whatever their retriever finds, which opens two doors for an attacker: instructions hidden in a page the bot retrieves (indirect prompt injection), and pages written to be retrieved for a target question so the bot repeats a false answer (knowledge poisoning). Universities are deploying these chatbots for admissions, financial aid and IT help, so getting the security right early matters.

Research questions

  1. How easily can a planted page, or a crafted question, make a campus chatbot give a wrong answer, leak its instructions or follow hidden commands?

    Hypothesis
    When nothing checks retrieved text, one planted page that matches a common question is enough to change the answer.
    How we would test it
    Red-team a copy of the campus chatbot with planted pages and crafted questions, and measure attack success by question type.

  2. Does hybrid retrieval (keyword plus vector search, with query rewriting) make poisoning easier or harder than vector search alone?

    Hypothesis
    Keyword search favors keyword-stuffed pages while query rewriting spreads retrieval over more passages, so the net effect depends on the attack.
    How we would test it
    Run identical attacks against vector-only and hybrid retrieval with the same language model and prompts.

  3. Which defenses (filtering retrieved text, requiring citations, a second model as a checker) reduce attacks without making answers worse?

    Hypothesis
    Source allowlists block most attacks but drop useful unofficial answers; a checker model catches contradictions at a latency cost.
    How we would test it
    For each defense and combination, measure attack success, answer quality on clean questions and response time.

Expected contributions

  • A red-team test set for campus chatbots.
  • A measured comparison of retrieval designs under attack.
  • Defenses tuned so that they block attacks without breaking good answers.

Approach

  1. SandboxRebuild our chatbot on a private copy of public pages; nothing touches live systems.
  2. Attack suitePrompt injection and poisoning attacks from the reading list, adapted to campus questions.
  3. MeasureAttack success, answer quality and cost for each retrieval setting.
  4. DefendAdd and compare guards.
  5. SharePublish the benchmark questions and a deployment checklist for universities.

Discussion

If it works

A tested set of defenses for campus chatbots, and a red-team checklist others can reuse.

Where it could fail

  • Attacks change quickly, so a defense that holds today may not hold next year.
  • Testing must stay on a copy of the chatbot, never the live service.

How we will know

Attack success before and after each defense, and what each defense costs in answer quality.

Start here

A first month for a student joining this work, in 3 steps. Do them in order: each one uses what the one before produced.

Goal for the month: A small campus chatbot and a measured rate of planted instructions it follows.

Before you start: setup for every project
  1. Set up a workspace. Create a private Git repository for the project with folders for data/, src/, figures/ and notes/. Make a Python virtual environment (python -m venv .venv) and record every package you install in requirements.txt.
  2. Keep a lab notebook. Add a dated entry to notes/log.md each time you work: what you ran (the exact command), what came out, and what surprised you. This log is the first thing to share when you ask for help, and most of your paper's method section comes from it.
  3. Make every number reproducible. Fix random seeds, write down the dataset version and how you split it, and keep the script that produced each figure next to the figure. If you cannot regenerate a number with one command, it is not finished.
  4. Stay legal and ethical. Work only with public datasets, data you recorded yourself with everyone's consent, or systems you own. Never test an attack on a network, car, radio band or service that is not yours, and follow the safety note on this page.
  5. When you get stuck. Spend about an hour, then write down what you tried, what you expected and the exact error or plot, and ask. A precise question is much easier to answer than "it does not work".
  1. Step 1 · Week 1Read the risks
    • Read the papers below and the OWASP Top 10 for LLM applications.
    • Pick the two risks that matter most for a university chatbot and write why.

    You are done when you can explain indirect prompt injection with one example.

  2. Step 2 · Week 2Build the chatbot
    • Save a few public university web pages as text.
    • Build a small retrieval chatbot over them: split the pages into chunks, embed them, retrieve the closest chunks, and answer with a language model.

    You are done when the chatbot answers ten test questions from the pages, with the source chunk shown.

  3. Step 3 · Weeks 3 and 4Plant and measure
    • Add one page that contains a hidden instruction, in your local copy only.
    • Ask questions that retrieve it and count how often the answer follows the instruction.
    • Scan the chatbot with garak and compare its findings with yours.

    You are done when one table gives the follow rate for your planted page and garak's results.
