Explanations you can check: explainable intrusion and malware detection

Security analysts are asked to act on alerts from models they cannot see inside. This project tests whether today's explanation methods tell them the truth about why a detector fired, and builds explanations an analyst can check.

The question

Do today's explanation methods tell a security analyst the truth about why a detector fired?

Why it matters

Analysts must act on alerts quickly, explanation methods can disagree, and a convincing explanation can still be wrong about what the model used.

How we will test it

Measure agreement and faithfulness of LIME, SHAP and gradient methods on several detectors, plant known shortcuts to see which explainers find them, and run a study with analysts.

Why this matters

Explainability already runs through my applied AI work: our food fraud study (Expert Systems, 2025) compared LIME, SHAP and Google's What-If Tool on one model and showed what each can and cannot tell a food-safety analyst, and our employee attrition paper (LA-CCI, 2025) used explanations to find the factors behind people leaving. Security raises the stakes. An intrusion or malware alert has to be acted on quickly, different explanation methods can disagree about the same alert, and an explanation that looks convincing can still be wrong about what the model actually used. An honest explanation can also expose a detector that learned a shortcut, which links this project to the leak-free benchmark project.

Research questions

  1. For the same intrusion or malware detector, how often do LIME, SHAP and gradient-based explanations agree on the top reasons for an alert, and which of them are faithful to what the model really uses?

    Hypothesis
    Explainers agree on the top reason far more often than on the full ranking, and how faithful they are depends on the model family.
    How we would test it
    Measure rank agreement across explainers, and faithfulness with deletion and insertion tests, on several detectors and datasets.

  2. Can explanations reliably expose shortcuts, such as a detector keying on capture artifacts instead of attack behavior?

    Hypothesis
    Faithful explainers surface a planted shortcut reliably; unfaithful ones can hide it.
    How we would test it
    Plant known shortcuts in training data and count how often each explainer names them as a top reason.

  3. Where does a small interpretable model (rules or a shallow tree) match a black-box detector closely enough to replace it?

    Hypothesis
    On header-level features, a shallow tree or rule list matches the black box on most traffic types.
    How we would test it
    Distill each detector into trees and rule lists, and report fidelity to the original, accuracy and model size.

  4. Do explanations help analysts triage alerts faster and more accurately, or only make them more confident?

    Hypothesis
    Explanations speed up triage but can also make analysts more confident in wrong alerts.
    How we would test it
    A controlled study with students and practitioners triaging alerts with and without explanations, measuring time, accuracy and confidence.

Expected contributions

  • A faithfulness test suite for explanations of security models.
  • Evidence on whether explanations reveal shortcuts.
  • Small, readable detectors that match black boxes where they can, and a user study on analyst triage.

Approach

  1. DetectorsTrain intrusion and Android malware detectors on public datasets from our earlier work.
  2. ExplainGenerate LIME, SHAP and gradient-based explanations for the same alerts.
  3. MeasureScore faithfulness by removing top features, plus stability and sparsity.
  4. Shortcut huntPlant known artifacts in the data and see which methods find them.
  5. Analyst studyA small, IRB-approved study with student analysts triaging alerts.

Discussion

If it works

Analysts get explanations they can verify, and learn when not to trust one.

Where it could fail

  • Faithfulness is hard to measure without ground truth; planted features help but are artificial.
  • A faithful explanation can still be too complex to act on.

How we will know

Whether explanations recover planted features, how far different methods agree, and whether they help an analyst decide.

Start here

A first month for a student joining this work, in 3 steps. Do them in order: each one uses what the one before produced.

Goal for the month: A security detector with explanations, and a deletion test showing whether those explanations can be trusted.

Before you start: setup for every project
  1. Set up a workspace. Create a private Git repository for the project with folders for data/, src/, figures/ and notes/. Make a Python virtual environment (python -m venv .venv) and record every package you install in requirements.txt.
  2. Keep a lab notebook. Add a dated entry to notes/log.md each time you work: what you ran (the exact command), what came out, and what surprised you. This log is the first thing to share when you ask for help, and most of your paper's method section comes from it.
  3. Make every number reproducible. Fix random seeds, write down the dataset version and how you split it, and keep the script that produced each figure next to the figure. If you cannot regenerate a number with one command, it is not finished.
  4. Stay legal and ethical. Work only with public datasets, data you recorded yourself with everyone's consent, or systems you own. Never test an attack on a network, car, radio band or service that is not yours, and follow the safety note on this page.
  5. When you get stuck. Spend about an hour, then write down what you tried, what you expected and the exact error or plot, and ask. A precise question is much easier to answer than "it does not work".
  1. Step 1 · Week 1Read the explanation papers
    • Read the papers below.
    • Note how each one decides whether an explanation is faithful to the model.

    You are done when you can describe at least two ways to test an explanation.

  2. Step 2 · Weeks 2 and 3Train and explain
    • Train a malware detector on CIC-AndMal2020 features, or an intrusion detector.
    • Explain twenty alerts with SHAP and with a gradient method from Captum, and save both rankings.

    You are done when each alert has two feature rankings saved to disk.

  3. Step 3 · Week 4Run the deletion test
    • For each alert, remove the top features in ranked order and watch the model's score fall.
    • Repeat with features removed in random order, and compare the two curves for each method.

    You are done when one chart per method shows ranked vs random deletion, averaged over the twenty alerts.

Tools and data

  • SHAPExplanations based on Shapley values.
  • CaptumModel interpretability for PyTorch.
  • CIC-AndMal2020 datasetAndroid malware in 14 categories and 191 families.

Finished the month? Email me your log, your figures and one paragraph on what you would do next. Writing it up? Follow the LaTeX and Overleaf guide for templates, citations, figures and the checks to run before you submit.
