Naming the app without reading the traffic

Encryption hides what is inside a packet, but not its size, its timing or its direction. This project asks how much that metadata reveals, how to use it to manage and secure networks without decrypting anything, and how to protect users from the same leak.

Why this matters

Almost all traffic is now encrypted. Network operators still need to know which applications and devices are on their network to manage and secure it, and they should not have to break encryption to find out. The same metadata that helps them is also a privacy risk: earlier work has shown that packet sizes and timing can identify apps and websites behind encryption.

My group already identifies IoT devices from single packet headers (ICISSP 2024) and evolves compact feature sets with a genetic algorithm (Electronics 2024). This project extends that line to encrypted flows, adding explainable AI and language models fine-tuned on traffic, and it studies defenses as seriously as attacks.

Research questions

  1. Which flow metadata (packet sizes, timing, direction, handshake fields) identifies an app or service from encrypted traffic, and how few features are needed?

    Hypothesis
    A small, evolved subset of size and timing features identifies most apps, as feature selection did for device fingerprints.
    How we would test it
    Run evolutionary feature selection on labeled encrypted captures and compare accuracy and feature count with using every feature.

  2. Can explanations and language models fine-tuned on traffic make these classifiers more accurate on unseen apps, or easier to audit, and at what cost?

    Hypothesis
    Explanations show which flow traits drive each decision, and fine-tuned language models help most on apps not seen in training.
    How we would test it
    Compare classical, sequence and fine-tuned language models on the same splits, auditing each one's top features with explanations.

  3. Which defenses (padding, timing changes, traffic shaping) protect users against these classifiers, and what do they cost in bandwidth and delay?

    Hypothesis
    Padding alone leaves timing leaks; combined defenses cut accuracy sharply but cost bandwidth and delay.
    How we would test it
    Apply each defense to captured traffic, retrain the classifier on defended traffic, and report accuracy against overhead.

Expected contributions

  • A traffic classifier that never decrypts payloads, built on evolved features.
  • An explanation-based audit of what such classifiers rely on.
  • A measured privacy-versus-overhead trade-off for padding and shaping defenses.

Approach

  1. CaptureRecord labeled encrypted traffic from phones, laptops and IoT devices in a lab network we control.
  2. ExtractTurn each flow into sizes, timing, direction and handshake fields; never read payloads.
  3. EvolveSelect compact feature sets with a genetic algorithm, as in our incident-identification work.
  4. Model and explainCompare classical models, sequence models and fine-tuned language models, and audit each with explanations.
  5. DefendApply padding and shaping, retrain the classifier, and measure accuracy against overhead.

Only traffic from our own lab devices or from public datasets is used. The project never decrypts other people's traffic.
