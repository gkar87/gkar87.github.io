Naming the app without reading the traffic

Encryption hides what is inside a packet, but not its size, its timing or its direction. This project asks how much that metadata reveals, how to use it to manage and secure networks without decrypting anything, and how to protect users from the same leak.

The question

How much do packet sizes and timing reveal about the app behind encrypted traffic, and how can users be protected?

Why it matters

Operators need to manage networks without breaking encryption, and the same metadata is a privacy risk for users.

How we will test it

Evolve small feature sets on labeled encrypted captures, compare classical models with fine-tuned language models, and measure what padding and timing defenses cost.

Why this matters

Almost all traffic is now encrypted. Network operators still need to know which applications and devices are on their network to manage and secure it, and they should not have to break encryption to find out. The same metadata that helps them is also a privacy risk: earlier work has shown that packet sizes and timing can identify apps and websites behind encryption.

My group already identifies IoT devices from single packet headers (ICISSP 2024) and evolves compact feature sets with a genetic algorithm (Electronics 2024). This project extends that line to encrypted flows, adding explainable AI and language models fine-tuned on traffic, and it studies defenses as seriously as attacks.

Research questions

  1. Which flow metadata (packet sizes, timing, direction, handshake fields) identifies an app or service from encrypted traffic, and how few features are needed?

    Hypothesis
    A small, evolved subset of size and timing features identifies most apps, as feature selection did for device fingerprints.
    How we would test it
    Run evolutionary feature selection on labeled encrypted captures and compare accuracy and feature count with using every feature.

  2. Can explanations and language models fine-tuned on traffic make these classifiers more accurate on unseen apps, or easier to audit, and at what cost?

    Hypothesis
    Explanations show which flow traits drive each decision, and fine-tuned language models help most on apps not seen in training.
    How we would test it
    Compare classical, sequence and fine-tuned language models on the same splits, auditing each one's top features with explanations.

  3. Which defenses (padding, timing changes, traffic shaping) protect users against these classifiers, and what do they cost in bandwidth and delay?

    Hypothesis
    Padding alone leaves timing leaks; combined defenses cut accuracy sharply but cost bandwidth and delay.
    How we would test it
    Apply each defense to captured traffic, retrain the classifier on defended traffic, and report accuracy against overhead.

Expected contributions

  • A traffic classifier that never decrypts payloads, built on evolved features.
  • An explanation-based audit of what such classifiers rely on.
  • A measured privacy-versus-overhead trade-off for padding and shaping defenses.

Approach

  1. CaptureRecord labeled encrypted traffic from phones, laptops and IoT devices in a lab network we control.
  2. ExtractTurn each flow into sizes, timing, direction and handshake fields; never read payloads.
  3. EvolveSelect compact feature sets with a genetic algorithm, as in our incident-identification work.
  4. Model and explainCompare classical models, sequence models and fine-tuned language models, and audit each with explanations.
  5. DefendApply padding and shaping, retrain the classifier, and measure accuracy against overhead.

Only traffic from our own lab devices or from public datasets is used. The project never decrypts other people's traffic.

Discussion

If it works

Networks can be managed and secured from metadata alone, and users can be protected from the same leak.

Where it could fail

  • Padding and newer protocols may hide most of the signal.
  • The same methods could be used for surveillance, so defenses are part of the project.

How we will know

Identification accuracy from encrypted flows, with and without padding defenses, and the bandwidth each defense costs.

Start here

A first month for a student joining this work, in 3 steps. Do them in order: each one uses what the one before produced.

Goal for the month: An encrypted-traffic classifier built from sizes and timing only, and a measured cost for padding that defeats it.

Before you start: setup for every project
  1. Set up a workspace. Create a private Git repository for the project with folders for data/, src/, figures/ and notes/. Make a Python virtual environment (python -m venv .venv) and record every package you install in requirements.txt.
  2. Keep a lab notebook. Add a dated entry to notes/log.md each time you work: what you ran (the exact command), what came out, and what surprised you. This log is the first thing to share when you ask for help, and most of your paper's method section comes from it.
  3. Make every number reproducible. Fix random seeds, write down the dataset version and how you split it, and keep the script that produced each figure next to the figure. If you cannot regenerate a number with one command, it is not finished.
  4. Stay legal and ethical. Work only with public datasets, data you recorded yourself with everyone's consent, or systems you own. Never test an attack on a network, car, radio band or service that is not yours, and follow the safety note on this page.
  5. When you get stuck. Spend about an hour, then write down what you tried, what you expected and the exact error or plot, and ask. A precise question is much easier to answer than "it does not work".
  1. Step 1 · Week 1Read the papers
    • Read the papers below.
    • List the features each attack uses: packet sizes, timing, direction, or bursts.

    You are done when your list covers every paper.

  2. Step 2 · Week 2Turn flows into features
    • Download the ISCX VPN-nonVPN data.
    • Split it into flows and compute, per flow, packet sizes, inter-arrival times and directions.

    You are done when you have one feature table, one row per flow, with its application label.

  3. Step 3 · Weeks 3 and 4Classify, then defend
    • Train a nearest-profile classifier and report accuracy per application category.
    • Pad packets to fixed sizes (or add dummy packets), retrain, and measure both the new accuracy and the extra bytes sent.

    You are done when one chart shows accuracy against padding overhead.

Tools and data

  • ISCX VPN-nonVPN datasetLabeled encrypted traffic across application categories.
