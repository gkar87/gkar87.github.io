Catching ghost vehicles in V2X messages

Connected cars broadcast their position and speed many times a second, and other cars act on those messages. This project detects messages that describe cars that are not there.

The question

Can a connected car tell when a V2X message describes a vehicle that is not there?

Why it matters

A signature proves who sent a message, not that it is true, and a fake car braking hard ahead can trigger emergency braking behind it.

How we will test it

Evaluate plausibility checks on public misbehavior datasets and simulated attacks, add roadside and on-board sensors, and profile each detector on embedded boards.

Why this matters

Vehicle-to-everything (V2X) messages are signed, so a receiver can tell that a message came from a certified sender. A signature cannot tell whether the message is true. A compromised unit, or an insider with valid credentials, can report a ghost car braking hard ahead and trigger emergency braking behind it. Detecting that kind of misbehavior has to look at what the messages say and check it against physics and against independent sensors.

My research statement's first direction is exactly this: detecting spoofed, jammed or manipulated sensor and V2X data on vehicle and roadside hardware. It builds on our roadside detection of GPS jammers (ACM CCS 2014) and on traffic estimation at vehicular edge nodes (ACM/IEEE SEC 2017).

Research questions

  1. Which plausibility checks on position, speed and heading catch fake vehicles in V2X messages, and how do they trade detection against false alarms?

    Hypothesis
    Simple physical checks catch crude ghosts; attackers who obey physics can only be caught with evidence from independent sensors.
    How we would test it
    Evaluate checks on public misbehavior datasets and on simulated attacks of rising sophistication.

  2. How much do roadside cameras, radar and other cars' reports add, and where are the coverage gaps an attacker can use?

    Hypothesis
    Fusing independent sensors closes most gaps, and the remaining risk sits where no independent sensor looks.
    How we would test it
    Simulate traffic with roadside and on-board sensor coverage, place attacks inside and outside it, and measure detection.

  3. Can misbehavior detection run within the latency and memory budget of roadside and on-board units?

    Hypothesis
    Single-message checks fit easily on board; fusing several sensors is the costly step and belongs on roadside edge computers.
    How we would test it
    Profile each detector on embedded boards at realistic message rates.

Expected contributions

  • A layered ghost-vehicle detector combining plausibility checks with roadside and on-board sensors.
  • A coverage analysis showing where attacks can still hide.
  • Run-time profiles on roadside and on-board hardware.

Approach

  1. Start from dataUse public misbehavior datasets with labeled attacks.
  2. SimulateAdd ghost vehicles of rising sophistication in a traffic and network simulator.
  3. Check plausibilityTest each message against physics and the sender's own history.
  4. Fuse sensorsCross-check against simulated roadside cameras and on-board radar.
  5. DeployProfile the detectors on embedded boards at realistic message rates.

All attacks run in simulation or on recorded data. Nothing is broadcast on real V2X channels.

Discussion

If it works

Cars can ignore messages about vehicles that do not exist, before acting on them.

Where it could fail

  • Simulated traffic is cleaner than real roads.
  • Several coordinated fake senders are much harder to catch than one.

How we will know

Detection rate and time to detect across traffic densities and attack types, with false alarms on honest traffic.

Start here

A first month for a student joining this work, in 3 steps. Do them in order: each one uses what the one before produced.

Goal for the month: A plausibility check that catches falsified V2X positions, tested on a public dataset and in simulation.

Before you start: setup for every project
  1. Set up a workspace. Create a private Git repository for the project with folders for data/, src/, figures/ and notes/. Make a Python virtual environment (python -m venv .venv) and record every package you install in requirements.txt.
  2. Keep a lab notebook. Add a dated entry to notes/log.md each time you work: what you ran (the exact command), what came out, and what surprised you. This log is the first thing to share when you ask for help, and most of your paper's method section comes from it.
  3. Make every number reproducible. Fix random seeds, write down the dataset version and how you split it, and keep the script that produced each figure next to the figure. If you cannot regenerate a number with one command, it is not finished.
  4. Stay legal and ethical. Work only with public datasets, data you recorded yourself with everyone's consent, or systems you own. Never test an attack on a network, car, radio band or service that is not yours, and follow the safety note on this page.
  5. When you get stuck. Spend about an hour, then write down what you tried, what you expected and the exact error or plot, and ask. A precise question is much easier to answer than "it does not work".
  1. Step 1 · Week 1Read the papers
    • Read the misbehavior detection survey and the VeReMi paper below.
    • List the attack types in VeReMi and what a simple check could catch.

    You are done when each attack type has a check you could write.

  2. Step 2 · Weeks 2 and 3Write a plausibility check
    • Download one VeReMi dataset and parse the received messages with their ground truth.
    • Flag a message when the claimed position or speed is impossible given the sender's previous message.

    You are done when your check runs over the whole dataset in one script.

  3. Step 3 · Week 4Measure and move to simulation
    • Report detection and false alarms per attack type.
    • Follow the Veins tutorial to run a small simulation and plan how you would run your check inside it.

    You are done when you have a results table and a running Veins example.
